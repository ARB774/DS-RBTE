# Карточка проекта и версии

Читайте этот файл при создании проекта, восстановлении сессии и фиксации перехода.

## Обязательные поля

Сохраняйте карточку в принятом пользователем документе. Если имя и место не заданы, запросите их: не придумывайте название артефакта.

```yaml
project:
  name: ""
  owner_role: ""
  confidentiality: ""
  system_boundary: ""
training:
  result: ""
  current_state: "S0"
  verification_class: ""
  method: ""
  assessment: ""
  model: ""
product:
  type: ""
  accepted_version: ""
  draft_version: ""
evidence:
  established: []
  reported: []
  interpretations: []
  hypotheses: []
  unknown: []
cases: []
assumptions: []
sources: []
open_gap: ""
next_step: ""
stop_or_return_condition: ""
visualization:
  template: "tucha-template.svg"
  version: ""
  rendered_asset: ""
  render_status: "rendered|attached|blocked"
  active_element: ""
```

Адаптируйте структуру к принятому формату проекта, но не теряйте смысл полей.

## Статусы утверждений

- **Установлено** — есть наблюдаемые данные с восстанавливаемым происхождением.
- **Сообщено** — известен источник сообщения, но обстоятельство отдельно не проверено.
- **Интерпретация** — объяснение известных данных.
- **Гипотеза** — проверяемое предположение о неизвестном.
- **Неизвестно** — сведений недостаточно; указан вопрос или способ проверки.

Не повышайте статус по согласию участника, убедительности текста или правдоподобию.

## Версии рабочих продуктов

- Для профиля используйте `P0` — первая самостоятельная попытка, `P1` — целостный предварительный профиль, `P2` — проверенная в принятой границе версия либо обоснованная остановка с планом проверки.
- Для других продуктов используйте уже принятую проектом нумерацию. Не вводите новую схему имён без согласования.
- Сохраняйте предыдущую принятую версию и причины изменения; не перезаписывайте историю молча.
- Указывайте, что именно изменилось, на основании каких данных и какую проверку нужно повторить.

## Случаи и конфиденциальность

Если проект требует обезличивания, обозначайте организации и эпизоды кодами `C1`, `C2`, `C3` и далее. Не фиксируйте имена, названия компаний, города или иные идентификаторы. Для каждого случая сохраняйте:

- почему он выбран;
- период и границу;
- наблюдения и сообщения;
- связь с критическими пунктами профиля или причинной модели;
- контрастные данные;
- неизвестное и следующий способ проверки.

## Карта предположений

Для каждого предположения сохраняйте:

```yaml
- id: "P(B-D)-1"
  statement: ""
  link: "B-D"
  area: ""
  status: "established|possible|unknown|rejected"
  evidence_for: []
  evidence_against: []
  exceptions: []
  limiting_role: ""
  decision: "keep|edit|split|exclude|challenge|selected"
```

## Фиксация источников MCP

Для каждого содержательно применённого паттерна запишите:

```yaml
- publication: "Pack-TOC"
  pattern_id: "TOCT.7"
  server_revision: "v1:...|unknown"
  sections_read: ["Problem frame", "Solution", "Conformance Checklist"]
  limitation: ""
```

Не выдавайте локальный Git SHA за серверную редакцию.

## Восстановление следующей сессии

1. Прочитайте карточку и указанное ТЗ.
2. Назовите последнюю принятую версию и текущую стадию.
3. Проверьте, не противоречит ли новый запрос принятому входу.
4. Покажите актуальный рабочий продукт, если вопрос требует его видеть.
5. Продолжите с записанного `next_step`; не перестраивайте принятые продукты без причины.
